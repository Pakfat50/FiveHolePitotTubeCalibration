# 製品コード開発ルール

本書は、現在の製品コードの実装と設計上の責務に基づく開発ルールである。機能追加・不具合修正・APIドキュメント更新を行う際は、本書と[トレーサビリティ運用ルール](traceability_rules.md)を併用する。

製品コードの実装を変更しないドキュメント修正では、製品コードに合わせてドキュメント・リンク・対応表を修正する。リンク切れや対応表の不整合を直すために、製品コードの挙動を変更してはならない。

## 1. 適用範囲

対象は、リポジトリ直下の以下の製品コードである。

| 区分 | 対象モジュール | 役割 |
|---|---|---|
| ドメインモデル | `models.py` | 値・設定・較正計画など、層間で共有するデータモデル |
| Core | `validation.py`、`scan.py`、`transform.py`、`positioning.py`、`limits.py` | 入力検証、走査点生成、角度変換、位置補正、リミット評価 |
| Application | `calibration_service.py`、`controller.py` | 較正計画の組み立て、入力状態と生成可否の管理 |
| Infrastructure | `repositories.py` | 設定・初期化Gコード・生成Gコードのファイル入出力 |
| Presentation | `map_view.py`、`simulation.py`、`gui.py` | マップ表示、シミュレーション、Tkinter GUI |
| Composition root | `main.py` | 依存オブジェクトの生成・注入、UIテーマとレイアウトの初期設定 |
| Gコード | `gcode.py` | 完成済みの較正計画からGコードを整形して出力 |

## 2. 基本原則

1. 要求仕様・ユースケース・アーキテクチャ設計を確認してから実装する。
2. 1つの計算責務を複数の層や画面に複製しない。計算結果は共有モデルまたはApplicationサービスを経由して利用する。
3. UI、ファイル入出力、Gコード出力の各処理をCoreの計算ロジックに混在させない。
4. 製品コードAPIの公開名を変更・追加・削除する場合は、要求・設計・テスト・APIドキュメントの対応を同時に更新する。
5. 既存の要求ID、ユースケースID、テストIDは変更・再利用・欠番の詰め替えをしない。
6. 製品コードの挙動に関係しないリンク修正やドキュメント修正で、製品コードを変更しない。
7. 数値計算は決定的にする。丸め、単位、角度の向き、前回値の扱いを暗黙に変更しない。

## 3. 層と依存関係

### 3.1 ドメインモデル

`models.py`は、Core・Application・Infrastructure・Presentationの各層で共有する値を定義する。データモデルはドメイン上の意味を表し、GUI、Matplotlib、ファイルI/Oに依存しない。

- `Severity`、`ValidationIssue`、`ValidationResult`で検証結果を表現する。
- `AxisRange`、`AxisLimits`、`CalibrationSettings`で設定値と軸範囲を表現する。
- `CalibrationPoint`、`AxisCommand`、`PointEvaluation`で走査点、軸指令、評価結果を表現する。
- `CalibrationPlan`を、マップ表示・シミュレーション・Gコード生成が共有する単一の較正計画とする。
- 新しい値を追加するときは、単なる辞書や画面ウィジェットの状態ではなく、ドメインモデルとして表現できるかを確認する。

### 3.2 Core

`validation.py`、`scan.py`、`transform.py`、`positioning.py`、`limits.py`は、画面やファイルに依存しない計算責務を持つ。

- `InputValidator.validate`は入力をまとめて検証し、検出できる問題を検証結果として返す。最初の1件だけで打ち切らない。
- 角度範囲は最小値が最大値より小さいこと、点数は必要な最小数を満たすこと、長さ・保持時間・送り速度は実装で定めた正の有限値または下限を満たすことを検証する。
- `ScanPlanner.generate_points`は、AoAを外側、AoSを内側の走査軸とし、範囲の両端を含める。蛇行走査では奇数行のAoS順を反転する。
- `AngleTransformer.transform`は、物理モデルのピッチ変換後にピトー軸ロールを適用する。等価解、前回角度との連続性・移動量、ロール絶対値を考慮して解を選ぶ。原点などの特別値についても決定的な結果にする。
- `PositionCompensator.calculate_xy`はピッチによるXY位置補正を計算する。ロールをXY先端位置の計算に混入させない。
- `LimitEvaluator.evaluate`はX/Yを範囲内に収めるためのクランプと偏差を評価する。Z/Aはクランプせず、回転軸の範囲外をエラーとして扱う。
- 計算式、軸の意味、単位、境界条件は関数のdocstringとテストで明示する。UI側で同じ計算式を再実装しない。

### 3.3 Application

`CalibrationService`は、走査点生成・角度変換・位置補正・リミット評価を組み合わせて`CalibrationPlan`を構築する。`CalibrationController`は入力状態と計画の有効性を管理する。

- `CalibrationService.build_plan`を、較正計画を組み立てる責務の中心とする。
- `CalibrationPlan`をマップ表示、シミュレーション、Gコード生成の共通入力とする。各利用先が独自に再計算してはならない。
- 走査中の前回Z/Aを次の点へ引き継ぎ、角度選択の連続性を保つ。
- X/Yの最大偏差は計画全体で集計する。Z/Aの範囲エラーは計画に記録し、生成可否へ反映する。
- `CalibrationController`は入力変更のたびに同じ検証経路を通す。入力が不正なときは計画を破棄し、有効な入力だけで計画を構築する。
- `can_generate`は、有効な検証結果、計画の存在、回転軸エラーがないことを満たす場合だけ真にする。XY偏差だけでGコード生成を一律禁止しない。
- 設定ファイルの適用も画面入力と同じ検証経路を利用する。

### 3.4 Infrastructure

`repositories.py`はファイル入出力を担当し、計算や画面操作を担当しない。

- 設定はUTF-8のCSVキー・バリュー形式で読み書きする。現在の形式にスキーマバージョンを追加したり、独自の別形式を併存させたりしない。
- 必須キーをすべて読み取り、検証済みの設定オブジェクトを一括して構築する。不完全な設定を部分適用しない。
- 設定読み込みに失敗した場合は`SettingsLoadError`など想定した例外として上位へ返す。Repository内で画面通知を行わない。
- 初期化GコードはUTF-8で読み込み、生成Gコードは`GCodeRepository.save`で保存する。
- パス、エンコーディング、読み書き失敗時の扱いを変更するときは、要求・テスト・ユーザー通知を同時に見直す。

### 3.5 Presentation

`map_view.py`、`simulation.py`、`gui.py`は表示・操作を担当し、較正計算の正本にはならない。

- `MainWindow`はTkinterの画面、入力欄、ボタン、通知を担当し、計算サービス・Repository・Gコード生成器・各Viewを依存性注入で受け取る。
- 製品コードAPIや内部メソッドを画面側から直接再実装せず、Applicationサービスが作成した`CalibrationPlan`を表示・出力する。
- 入力エラーは該当欄を`#FFECEC`で示し、通常の枠線とレイアウトを維持する。エラー通知は画面内の非モーダルなステータス領域で行う。
- GUIの表示文言は日本語を基本とし、API名・軸名・Gコードなど技術上必要な英語表記は意味を変えずに使用する。
- `CalibrationMapView`は横軸をAoS、縦軸をAoAとする。色分けは正常点とXY飽和点を基本とし、Z/Aエラーは`x`マーカーで示す。表示のために評価結果を変更しない。
- `SimulationController`と`SimulationView`は、同じ計画を3つの表示（側面、正面、較正マップ）で同期する。スライダーは時間の再計算ではなく点単位の移動とする。
- シミュレーション時間の既定値は約10秒とし、実機の保持時間をそのまま再生時間にしない。アニメーションオブジェクトはインスタンスのメンバーとして保持する。
- 一時停止・再開・シーク・再スタート・完了の状態遷移は、既存のコールバックと状態管理を通す。

### 3.6 Composition root

`main.py`はアプリケーションの組み立て場所とする。

- `build_application`でValidator、Service、Controller、Repository、Gコード生成器、MapView、SimulationView、MainWindowの依存関係を生成・注入する。
- `main.py`に較正計算、CSVの解析、画面イベントごとの業務判断を追加しない。
- `configure_ui_theme`と`tune_vertical_layout`はUIテーマ・フォント・レイアウトの初期設定に限定する。
- 日本語フォントの候補とフォールバックを維持し、環境依存のフォントを単一名で固定しない。

## 4. 較正計算と軸のルール

- 入力角度は度、位置はmm、送り速度はGコードの`G94`における単位/分、保持時間は秒として扱う。単位変換を追加するときは入力、モデル、表示、Gコード、テストの全箇所を確認する。
- AoA・AoSと、実際にモータへ出力するX/Y/Z/Aの意味を混同しない。軸の対応は`CalibrationSettings`、`AxisLimits`、`AxisCommand`の定義を正本とする。
- 角度変換の順序、等価解の選択、前回値からの連続性は`AngleTransformer`に集約する。
- X/Yの物理補正とリミット処理は、それぞれ`PositionCompensator`と`LimitEvaluator`に集約する。
- 偏差を表示する場合は理想値と実指令値を区別する。クランプ後の値を理想値として扱わない。
- 新しい軸、制約、補正を追加する場合、モデル・計算・計画・表示・Gコード・テストの各責務を列挙してから実装する。

## 5. Gコード生成のルール

`GCodeGenerator`は完成済みの`CalibrationPlan`を整形する。Gコード生成時に角度変換、位置補正、リミット評価を再実行しない。

- ユーザーが指定した初期化Gコードを保持し、その後に`$H`、`G21`、`G90`、`G94`を出力する。
- 各較正点はX/Y/Z/Aを同時に含む1つの`G01`移動として出力し、送り速度は`F`で指定する。
- 各点の移動後に`G04 P<秒>`を出力して保持時間を表現する。
- 軸値は現在のフォーマット規則に従って小数点以下6桁まで整形する。丸め方法を独自に変えない。
- コメント出力は設定で有効化できるが、コメントの有無で移動指令や保持指令の意味を変えない。
- 最終点の後に自動ホームや原点復帰を追加しない。
- Gコード出力仕様を変更した場合は、生成結果、保存処理、テスト仕様書、対応する要求・設計リンクを更新する。

## 6. 永続化とエラー通知のルール

- 読み込んだ設定値を検証せずに画面へ反映しない。
- 必須値が不足した設定、型変換できない設定、範囲外の設定は一部だけ適用しない。
- ファイルI/Oの例外は、ユーザーが原因を把握できる情報を添えてGUIの非モーダルなステータス領域へ伝える。
- 例外を握りつぶして成功扱いにしない。逆に、表示層以外からTkinterのダイアログを直接呼び出さない。
- 保存完了・読み込み完了・入力不備・Gコード生成不可の状態を区別して表示する。

## 7. APIとdocstringのルール

- 製品コードの公開クラス・公開メソッドには、mkdocstringsで意味が伝わるGoogle Style docstringを記述する。
- docstringには、目的、引数、戻り値、発生し得る例外、単位・境界条件・重要な不変条件を必要に応じて記載する。
- docstringは実装と一致させる。実装していない挙動を説明として追加しない。
- コメントは処理内容の逐語的な説明ではなく、計算順序、設計上の制約、なぜその扱いにするかを説明する。
- `docs/api.md`の`:::`定義に含まれるモジュール・クラス・メソッドは、実際のモジュールパスと公開名を使用する。
- Markdownから製品コードAPIへリンクする場合は、生成されたAPIページの実在するアンカーを使用する。例えば`[[API:gui.MainWindow._collect_raw_input]]`のように正確なAPI名を指定し、推測したアンカーや製品コードページ以外の章をリンク先にしない。
- API名を変更した場合は、docstring、`docs/api.md`、要求・設計・テストの対応表、リンク監査を更新する。

## 8. テストとトレーサビリティ

- 新しい製品コードの変更は、対応する要求ID、ユースケースID、アーキテクチャ設計上の責務、単体テストIDまたはユースケーステストIDを明示する。
- 要求とアーキテクチャ設計のリンクは、対応するユースケースの3.1〜3.6に紐付ける。要求仕様の関連成果物には、正確なIDと成果物名を記載する。
- テスト仕様書の「モジュール/メソッド ↔ 単体テストID」では、テストIDを短縮表現で全番号記載し、各テストIDをテスト仕様書の該当テストへリンクする。
- 同表のモジュール名は製品コードAPIページの対応するモジュールへリンクする。メソッドは実在するAPIアンカーへリンクする。
- 製品コード側のAPI docstringとテストコード側のdocstringで、同じIDを別の意味に使わない。
- テストのdocstring形式は[テストコードドキュメンテーション規約](test_doxygen_guideline.md)に従う。
- リンク修正の検証では、公開HTMLでリンクの`href`と遷移先ページのアンカーを確認する。Markdown上でリンク記法があるだけでは完了としない。

## 9. 機能追加の手順

1. 要求仕様に新しい要求IDを追加し、関連するユースケースを明記する。
2. アーキテクチャ設計書の対応する3.1〜3.6のユースケース節に責務を追加する。
3. 必要なデータを`models.py`に追加し、計算責務をCore、組み合わせをApplication、入出力をInfrastructure、表示・操作をPresentationへ配置する。
4. `CalibrationPlan`を共有できるかを確認し、表示・シミュレーション・Gコード生成に同じ計画を渡す。
5. 正常系、境界値、異常系、既存機能への影響をテスト仕様書へ追加する。
6. 製品コードAPIとテストコードAPIのdocstringを更新し、対応表のID・モジュール・メソッド・リンクを更新する。
7. `mkdocs build --strict`相当のCIを実行し、未解決リンク、未定義アンカー、docstring警告を解消する。
8. デプロイ後に要求、アーキテクチャ、テスト、製品コードAPI、テストコードAPIのリンクを公開HTMLで確認する。

## 10. 禁止事項

- GUI、シミュレーション、Gコード生成器で同じ較正計算を個別に実装すること。
- `CalibrationPlan`を使わず、画面の表示値やGコード生成時に別の計算結果を作ること。
- Z/Aの範囲外を黙ってクランプして正常扱いにすること。
- XY偏差とZ/A回転軸エラーを同じ重大度で扱い、既存の生成可否ルールを変えること。
- 実機の保持時間をシミュレーション時間へそのまま流用すること。
- 設定値を一部だけ適用すること、または読み込み失敗を成功扱いにすること。
- 表示やファイルI/OのためにCoreへTkinter、Matplotlib、Repository依存を追加すること。
- APIアンカーを推測してリンクを作ること、または公開サイトの絶対URLをソースへ埋め込むこと。
- リンク切れの修正を理由に、製品コードやテストコードのロジックを変更すること。
