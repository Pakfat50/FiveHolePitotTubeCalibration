# テストコードドキュメンテーション規約

## 1. 目的

本規約は、Pythonテストコードをソースレビュー時に理解しやすくするとともに、MkDocsとmkdocstringsからテスト仕様・検証意図・検証根拠を生成できる状態を維持することを目的とする。

テストコードのコメントは「何を実行しているか」だけでなく、以下を第三者が追跡できることを重視する。

1. どのテスト仕様を実装しているか
2. 何を観測して合否を判定しているか
3. なぜその観測によって対象仕様を確認できるのか
4. どの要求・ユースケースへトレースするか

## 2. 基本形式（Googleスタイル）

Pythonでは、mkdocstringsのGoogle形式でテストメソッド直下に記述する。

```python
# TEST-UNIT-XXX
# Requirements: REQ-XXX-YYY
def test_example(self):
    """テストの目的を1文で記述する。

    TEST ID:
        TEST-UNIT-XXX: テスト仕様の概要を記述する。

        入力条件、操作、主な観測対象、および検証根拠を記述する。

    Preconditions:
        必要な事前条件がある場合のみ記述する。

    Postconditions:
        重要な事後状態がある場合のみ記述する。

    対応要求:
        REQ-XXX-YYY
    """
```

すべてのセクションを機械的に埋める必要はないが、各テストには目的、TEST ID、検証根拠を含める。

## 3. 各項目の役割

### 概要

テストの目的を短く記述する。テストメソッド名を日本語に直訳するだけではなく、確認したい振る舞いを明示する。

### `TEST ID:`

既存の `TEST-UNIT-*` または `TEST-UC-*` IDと、`docs/test_specification.md` に定義されたテスト仕様の要点を記述する。

テストIDは既存コメントにも残し、Doxygen docstring側にも記載する。これによりソース検索と生成ドキュメントの双方から追跡可能にする。

### 補足説明

必要に応じて、入力条件、操作、観測する戻り値・状態・描画要素・ファイル内容などを記述する。

実装手順の逐語説明ではなく、テスト意図の理解に必要な情報へ限定する。

### 検証根拠

最も重要な項目とする。

「assertしているから確認できる」ではなく、なぜそのassert対象が仕様の成立を代表できるのかを記述する。

例:

- 境界値そのものと境界直下を比較するため、比較演算子の誤りを検出できる。
- 実planの全点座標と描画Artistの全offsetを集合比較するため、点の欠落・余分な点・軸取り違えを検出できる。
- Mockの呼出し引数と回数を確認するため、対象クラス自身の制御判断を依存先実装から分離して検証できる。
- 実ファイルへ保存後に再読込して完全一致比較するため、ファイルI/Oの副作用を実際に検証できる。

### `Preconditions:` / `Postconditions:`

特別な前提条件や、テスト後に保証されるべき状態が重要な場合に使用する。単純な単体テストでは省略してよい。

### `See Also:`

対応する要求IDを記述する。ユースケーステストでは既存の `# UseCase: UC-XX` を維持し、必要に応じて関連要求も記載する。

## 4. ファイル・クラス・補助メソッド

各テストファイルには、次の情報をモジュールdocstringとして記述する。

```python
"""対象機能の単体テスト。

File: test_xxx.py
対象機能、このファイルが検証する機能領域、対応するTEST ID範囲やテストレベルを記述する。
"""
```

テストクラスには、そのクラスが検証する責務を `@brief` で記述する。

テスト専用の補助メソッドには、通常の関数ドキュメントと同様に概要、必要に応じて `Args:`、`Returns:`、`Raises:` を記述する。また、補助メソッドの構造自体がテストの独立性に重要な場合は `設計根拠:` に設計根拠を記述する。

## 5. コメント品質ルール

- テストコードを逐語的に日本語へ翻訳しただけのコメントは避ける。
- 期待値の由来を明確にする。数式仕様の場合は、可能な限りテスト側で独立計算した期待値と比較する理由を記述する。
- Mockを使う場合は、なぜMockによる呼出し確認がその責務の検証になるのかを記述する。
- 組み合わせテストでは、どのモジュール間の受渡しを実経路で確認しているかを記述する。
- GUI/Matplotlibテストでは、画像の見た目ではなく、Axes、Artist、座標、色、ラベル等の観測可能な状態と仕様との対応を記述する。
- ファイルI/Oテストでは、一時ファイルを用いて実I/Oを確認していることと、その理由を記述する。
- 既存のTEST ID、要求ID、UC IDはコメント整備を理由に変更・再採番しない。
- テストロジックを変更する必要がある場合は、ドキュメンテーション変更とは別にTDD手順で扱う。

## 6. 将来の拡張

将来別のドキュメント生成ツールを導入する場合も、PythonソースとGoogle形式のdocstringを抽出対象とする。MkDocsの設定、生成物の配置、CIへの組込みは、本規約とは別タスクとして管理する。

Doxygen設定ファイル自体の追加・生成物の配置・CIへの組込みは、本規約とは別タスクとして実施する。
