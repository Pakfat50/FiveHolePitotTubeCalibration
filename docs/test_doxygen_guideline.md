# テストコード開発ルール

本書は、現在のテストコードの構成と実装方法に基づく開発ルールである。テストの追加・変更・テスト仕様との対応付け・テストAPIドキュメントの更新を行う際に適用する。

テストコードは、実装を通すだけの確認コードではなく、要求・設計で定めた振る舞いを再現可能な形で検証する成果物とする。テストコードの動作を変更しないドキュメント修正では、リンクや説明を実装に合わせて修正し、テストロジックやアサーションを変更してはならない。

製品コードの層構成と計算責務は[製品コード開発ルール](product_code_guideline.md)に、ID間のリンクと対応表は[トレーサビリティ運用ルール](traceability_rules.md)に従う。工程の順序は[開発プロセスルール](development_process_guideline.md)に従う。

## 1. 適用範囲

対象は、`tests/`配下の単体テスト、ユースケーステスト、共通テストヘルパー、およびテストコードAPIドキュメントである。

現在の主なテストファイルは次のとおりである。

| テストファイル | 主な対象 | テストID範囲・役割 |
|---|---|---|
| `test_validation.py` | `InputValidator` | 入力境界、異常値、複合エラー |
| `test_scan.py` | `ScanPlanner` | 格子、端点、走査順、蛇行 |
| `test_transform.py` | `AngleTransformer` | 座標変換、等価解、連続性、解選択 |
| `test_positioning.py` | `PositionCompensator` | XY補正式、ロール非依存性 |
| `test_limits.py` | `LimitEvaluator` | X/Y飽和、偏差、Z/A範囲エラー |
| `test_calibration_service.py` | `CalibrationService` | 複数Core処理の計画化、集約、生成可否 |
| `test_gcode.py` | `GCodeGenerator` | ヘッダ、4軸移動、保持、書式、終了位置 |
| `test_repositories.py` | Repository群 | CSV・UTF-8・保存・読み込み・I/Oエラー |
| `test_controller.py` | `CalibrationController` | 検証、plan再生成、状態遷移、生成可否 |
| `test_map_view.py` | `CalibrationMapView` | 軸、色、凡例、エラー表示、日本語フォント |
| `test_simulation.py` | `SimulationController`、`SimulationView` | フレーム、再生、3画面同期、表示幾何 |
| `test_gui.py` | `MainWindow` | 日本語UI、非モーダル通知、イベント制御 |
| `test_use_cases.py` | UC-01～UC-06 | 実オブジェクトを組み合わせたユーザー操作経路 |
| `test_support.py` | 共通ヘルパー | 正常設定、軸範囲、数値許容誤差の共通化 |

## 2. テストレベルと責務

### 2.1 単体テスト

単体テストは、対象の責務を他の責務から分離して確認する。Coreの数値計算や順序生成は実クラスを使い、依存先を注入できるControllerなどは依存先をMock化して制御判断を確認する。

- 1つの公開責務を中心に、正常系・境界値・異常系を構成する。
- Coreの数値計算は、テスト側で独立に計算した期待値、または仕様から直接導いた期待値と比較する。
- 離散値、点列、コマンド列は、点数だけでなく必要な全要素と順序を比較する。
- モジュール間の組み合わせ自体を主目的にしない。組み合わせを主目的にする場合はユースケーステストとして記述する。

### 2.2 ユースケーステスト

`test_use_cases.py`は、UC-01～UC-06のユーザー操作単位を検証する。`UseCaseHarness`で`InputValidator`、`CalibrationService`、`CalibrationController`、Repository、`GCodeGenerator`などの実オブジェクトを接続し、製品と同じ主要データ経路を通す。

- Mockで全体を置き換えず、複数モジュール間のデータ受渡し、状態遷移、最終的なユーザー操作可否を確認する。
- 単体テストで確認した個別の式を繰り返すのではなく、入力からplan、表示・保存・Gコード生成までの経路が成立することを確認する。
- ユースケーステストには`TEST-UC-NN-MM`と`UC-NN`を付与し、アーキテクチャ設計書の対応ユースケースへトレースする。
- ユースケーステストは、要求IDを主キーのように置き換えず、対応するUC IDを正本とする。

### 2.3 共通テストヘルパー

`test_support.py`の共通ヘルパーを、各テストの前提条件をそろえるために使用する。

- `make_settings`は全入力が有効な標準`CalibrationSettings`を生成し、各テストは確認対象だけを`overrides`で変更する。
- `make_limits`は非対象軸を十分広い範囲に固定し、対象軸だけを上書きする。
- 数値仕様の共通許容誤差は`ABS_TOL = 0.001`を使用する。仕様上の許容値が異なる場合は、テストのdocstringに根拠を記載する。
- 共通ヘルパーへ新しい既定値を追加する場合は、既存テストの意味が変わらないことを確認する。
- テスト間で変更可能なオブジェクトを共有しない。各テストで新しい設定、Service、Controller、View、TemporaryDirectoryなどを生成する。

## 3. 基本原則

1. テストは要求・設計で定めた振る舞いを検証し、実装内部の偶然の表現だけを固定しない。
2. Arrange（前提準備）・Act（対象処理）・Assert（結果判定）の境界を明確にする。
3. 1テストの主たる合否判定を1つの振る舞いに対応させる。類似条件を列挙する場合は`subTest`などで条件を明示する。
4. テストは順番に依存せず、単独実行しても同じ結果になるようにする。
5. 外部ネットワーク、実機、GRBL、利用者のホームディレクトリ、既存の本番ファイルに依存しない。
6. 浮動小数点は直接の完全一致を避け、仕様に応じた許容誤差で比較する。文字列、列挙値、点番号、状態値などの離散値は完全一致で比較する。
7. 期待値は、対象実装の内部値をそのまま再利用して作らない。数式、仕様、独立した基準データから構成する。
8. テストの弱体化を目的にアサーションを削除したり、常に成功するMockを設定したりしない。
9. 仕様変更によるテストロジックの変更と、docstring・リンクだけの変更を区別する。
10. 要求ID、UC ID、TEST IDは既存値を変更・再採番・再利用しない。

## 4. テストデータと境界値

### 4.1 正常系

- 正常系では、すべての非対象条件を既知の有効値に固定し、テスト対象の条件だけを明示する。
- 正常な較正設定から生成された`CalibrationPlan`を、必要に応じてマップ・シミュレーション・Gコード生成の入力に使用する。
- 生成点を確認するときは、件数、座標集合、順序、点番号を仕様に応じて確認する。

### 4.2 境界値と異常系

- `min == max`、`min > max`、許容下限、下限直下、上限、上限直上を区別して試験する。
- 点数、角度範囲、Lx/Ly、保持時間、Feed rate、X/Y/Z/A可動範囲は、それぞれの許容境界を直接確認する。
- 異常系では、無効判定だけでなく、エラー項目、エラー重大度、計画破棄、生成可否など、仕様が定める結果まで確認する。
- X/Y飽和警告とZ/A範囲エラーを別条件として試験し、両者が同時に発生する複合条件も確認する。
- 複数の入力不備を扱う場合は、最初の1件だけでなく、検出可能なエラーがまとめて返ることを確認する。

### 4.3 数値計算

- `AngleTransformer`では、原点、正負のAoA/AoS、象限、等価解、前回値による連続性、可動範囲による選択を確認する。
- 等価解が複数存在する場合、特定の表現だけを固定せず、物理的に入力角を再現することと、仕様の選択優先順位を確認する。
- `PositionCompensator`では正負ピッチ、寸法の極小値、ロールがXY補正へ影響しないことを確認する。
- `LimitEvaluator`では、X/Yはクランプ後の値と飽和フラグ・偏差を確認し、Z/Aはクランプせず回転エラーになることを確認する。
- 角度差や連続性を検証するときは、走査列全体の隣接点を確認し、代表1点だけで合格にしない。

## 5. 製品コード別のテスト方法

### 5.1 Validation、Scan、Transform、Position、Limits

- `InputValidator`は、正常設定、各入力項目の境界・異常値、複合エラー、有限性を確認する。
- `ScanPlanner`は、端点を含む等間隔性、AoA外側・AoS内側の順序、蛇行時の奇数行反転を確認する。
- `AngleTransformer`は、独立した式または物理量の再現性で確認し、等価解の採用理由をテスト意図に記載する。
- `PositionCompensator`は、ピッチの補正式を独立計算し、X/Yを個別に比較する。
- `LimitEvaluator`は、X/Yの上下限、偏差量、Z/Aの範囲外エラー、軸間の非干渉を確認する。

### 5.2 CalibrationService、CalibrationController

- `CalibrationService`は実クラスを使用し、走査・変換・位置補正・リミット評価が1つの`CalibrationPlan`へ正しく集約されることを確認する。
- plan内の理想指令値と実指令値、各点の評価状態、X/Y最大偏差、Z/A生成禁止フラグを必要に応じて確認する。
- 蛇行走査の順序と、隣接点のロール角連続性を同じplanから確認する。
- `CalibrationController`はValidatorとServiceをMock化し、検証が先に行われること、不正入力時にServiceを呼ばないこと、有効化後にplanを再生成することを呼出し引数・回数と状態で確認する。
- XY警告は生成可能、Z/A回転エラーは生成不可という状態の違いを個別に確認する。
- 設定適用は、通常の入力変更と同じ検証・再計算経路を通ることを確認する。

### 5.3 GCodeGenerator

- Gコードテストは、可能な限り実際の`CalibrationService`で生成したplanを入力し、Generatorの再計算に依存しないことを確認する。
- 初期化Gコード、`$H`、`G21`、`G90`、`G94`の存在と順序を確認する。
- すべての`G01`行にX/Y/Z/A/Fが含まれることを確認する。
- `G01`・`G04`の番号表記、Feed rate、保持時間、軸値の小数桁数を実出力文字列で確認する。
- コメント有効・無効の両方を確認し、コメント有無で移動指令の意味が変わらないことを確認する。
- 最終点の後に意図しないホームや原点復帰が追加されないことを確認する。
- 1つのGコード行だけを確認せず、全移動行を走査して書式を検証する。

### 5.4 Repository

- ファイルテストは`TemporaryDirectory`または一時ファイルを使用し、リポジトリ外の既存データを変更しない。
- 設定CSVは保存・読込の往復で全フィールドが一致することを確認する。
- `serpentine`、`output_comments`などのbool値、X/Y/Z/A全軸の範囲、UTF-8日本語、複数行を確認する。
- 構造不正、必須キー不足、値の変換失敗、存在しないファイルなどを、仕様で定めた例外として確認する。
- 読み込みが失敗したときに、部分的な設定オブジェクトが返らないことを確認する。
- Gコード保存は実ファイルを再読込して内容を比較する。

### 5.5 MapView、SimulationView、MainWindow

- GUI・Matplotlibテストは、スクリーンショットの見た目だけで合否を決めない。Axes、Artist、座標、色、ラベル、凡例、状態、依存先呼出しなどの観測可能な値を確認する。
- `CalibrationMapView`は横軸AoS・縦軸AoA、正常点とX/Y飽和点の色、Z/Aエラーのマーカー・凡例を確認する。Z/Aエラーのために不要な第3色を追加しない。
- `SimulationController`はprogress=0、progress=1、中間値が走査順の点へ対応することを確認する。再生時間が保持時間に依存しないことも確認する。
- `SimulationView`は横面図・正面図・較正点マップの同期、実ピッチ・実ロール、表示範囲、不要な表示要素の有無を、描画オブジェクトの状態で確認する。
- `MainWindow`は`build_ui=False`とMock依存を利用して、イベント制御をTk実体から分離して確認できる。必要な日本語ラベル、入力欄のエラー背景、既存メッセージ領域、非モーダル通知、ボタン状態、Repository・Controller・Viewの呼出しを確認する。
- OS依存の日本語フォントは、フォント一覧をMock化して日本語フォント選択と英語フォールバックを分けて確認する。

## 6. Mock、実I/O、実オブジェクトの使い分け

| 確認対象 | 原則 |
|---|---|
| Controllerの制御判断 | Validator・ServiceをMock化し、呼出し順、引数、回数、保持状態を確認する |
| Coreの計算 | 実クラスを使用し、独立した期待値と比較する |
| CalibrationServiceの計画化 | 実クラスを使用し、複数Coreの受渡しとplan集約を確認する |
| Repositoryのファイル処理 | 一時ファイルを用いた実I/Oで往復・例外を確認する |
| GCodeGenerator | 実planを入力し、出力文字列と全行を確認する |
| Matplotlib表示 | 実Axes・Artistを観測し、OS依存部だけをMock化する |
| MainWindowのイベント制御 | `build_ui=False`と依存Mockで外部UI構築から分離する |
| ユースケース | 実オブジェクトをHarnessで接続し、主要経路を通す |

Mockはテスト対象そのものを置き換えるために使用しない。Mockの呼出し確認は、対象クラスが依存先を正しい条件で呼び出す責務を検証する場合に限定する。

## 7. テストケースとdocstringの記述ルール

### 7.1 ファイル・クラス・補助メソッド

各テストファイルには、次の情報をモジュールdocstringとして記載する。

```python
"""対象機能の単体テスト。

File: test_xxx.py
対象機能、このファイルが検証する機能領域、対応するTEST ID範囲やテストレベルを記載する。
"""
```

テストクラスには、検証対象の責務を記載する。`setUp`を使う場合は、各テストを独立状態で開始する理由を記載する。

テスト専用の補助メソッドには、概要、必要に応じて`Args:`、`Returns:`、`Raises:`を記載する。共通値を隠すだけでなく、対象条件を分離して観測可能にする設計根拠を記載する。

### 7.2 テストメソッド

Pythonでは、mkdocstringsのGoogle形式でテストメソッド直下にdocstringを記載する。各テストには最低限、次を含める。

- `TEST-UNIT-NNN`または`TEST-UC-NN-MM`の正確なTEST ID
- テスト目的
- 入力条件・前提条件・操作の要点
- 期待結果とパスクライテリア
- その観測で仕様を確認できる検証根拠
- 重要な場合の`Preconditions:`、`Postconditions:`
- 対応要求または対応UC ID。ユースケーステストではUC IDを主たる対応先とする。

例：

```python
def test_example(self):
    """TEST-UNIT-XXX

    テスト目的:
        正常な設定が受理されることを確認する。

    テスト手順:
        1. 正常設定を入力する。
        2. 検証結果を取得する。
        3. is_validとERROR issueの有無を確認する。

    パスクライテリア:
        検証結果が有効で、エラーを含まないこと。

    検証根拠:
        公開検証結果を直接確認するため、正常入力を誤って拒否しないことを判定できる。

    See Also:
        REQ-XXX-YYY
    """
```

テストIDはソースコメントにも残し、docstring側にも記載する。ソース検索と生成テストAPIの双方から追跡できる状態を維持する。

### 7.3 コメント品質

- テストコードを逐語的に説明するだけのコメントは避け、テスト意図と期待値の由来を説明する。
- 「assertしているから確認できる」ではなく、なぜそのassert対象が仕様を代表するかを記載する。
- 数式仕様では、テスト側の独立計算と比較する理由を記載する。
- Mockでは、呼出し引数・回数の確認が対象クラスの制御責務の検証になる理由を記載する。
- 組み合わせテストでは、どのモジュール間の受渡しを実経路で確認するかを記載する。
- GUI/Matplotlibでは、画像比較ではなく、Axes・Artist・座標・色・ラベルなどを観測する理由を記載する。
- ファイルI/Oでは、実ファイルを使う理由と一時ファイルで副作用を隔離する方法を記載する。
- 要求本文をテストdocstringへ重複転記せず、要求IDとテストが確認する振る舞いを記載する。
- `See Also:`などの対応先は、実装とテスト仕様のIDに一致させる。

## 8. テストIDとトレーサビリティ

- 単体テストは`TEST-UNIT-NNN`、ユースケーステストは`TEST-UC-NN-MM`を使用する。
- 新しいテストには、対応する要求IDまたはUC ID、テスト仕様書の詳細行、対象製品コードAPIを明示する。
- 要求と単体テストの対応表では、要求IDは要求仕様書へ、テストIDはテスト仕様書の該当行へリンクする。
- 「モジュール/メソッド ↔ 単体テストID」対応表では、モジュール・メソッドを製品コードAPIの実在アンカーへリンクし、テストIDを短縮表示で全番号記載する。
- ユースケーステストは、UC IDからアーキテクチャ設計書3.1〜3.6の対応ユースケースへリンクする。
- テストコードAPIへのリンクは、実在する`tests.<module>.<class>.<method>`アンカーを使用する。
- テスト仕様書のID表示やコメント整備を理由に、TEST IDの番号だけを変更しない。
- テスト仕様とテストコードの内容が異なる場合は、テストコードへ合わせて勝手に仕様を変更せず、差分を明示して確認する。

### 8.1 セマンティックマーカー

Markdownの対応表・関連成果物では、公開サイトの絶対URLを直書きせず、次のマーカーを使用する。

| 用途 | マーカー例 |
|---|---|
| 要求仕様書 | `[[REQ:REQ-SIM-007]]` |
| アーキテクチャUC | `[[ARCH:UC-05]]` |
| 製品コードAPI | `[[API:simulation.SimulationController.start]]` |
| テスト仕様書 | `[[TESTSPEC:TEST-UNIT-126]]` |
| テストコード短縮表示 | `[[TESTCODE_SHORT:tests.test_simulation.TestSimulation.test_playback_duration_is_independent_of_hold_time]]` |

API名、テストID、アンカーは推測せず、生成HTMLの`id`で存在を確認する。

## 9. テスト追加・変更の手順

1. 変更対象の要求ID、対応UC、製品コードの責務、既存テストIDを確認する。
2. 正常系、境界値、異常系、複合条件、状態遷移のどこが影響を受けるかを整理する。
3. 単体テストでは対象責務に合わせて実クラス・Mock・実I/Oを選択する。
4. 複数モジュールを通るユーザー操作なら、`test_use_cases.py`へUC ID付きの組み合わせテストを追加する。
5. テストデータは`test_support.py`の正常基準値を利用し、確認対象だけを上書きする。
6. テストメソッド、クラス、ファイルのdocstringへTEST ID、目的、手順、パスクライテリア、検証根拠を記載する。
7. テスト仕様書の詳細、要求・UCとの対応、テストコードAPIのリンクを更新する。
8. 単体テストID対応表では短縮表示を維持したまま全番号を記載し、モジュール・メソッド・各テストIDを個別にリンクする。
9. `mkdocs build --strict`相当のCIとテスト実行を確認する。
10. デプロイ後にテスト仕様書・テストコードAPI・製品コードAPI・要求仕様書・アーキテクチャ設計書のリンクとアンカーを公開HTMLで確認する。

## 10. 禁止事項

- 製品コードの実装をコピーして期待値を作ること。
- すべての依存先をMock化して、実際のデータ受渡しや副作用を検証しないこと。
- 実機、ネットワーク、利用者固有のファイルへ接続し、テスト環境を壊すこと。
- 画面のスクリーンショットだけでGUI・Matplotlibの合否を判定すること。
- X/Y飽和警告とZ/A生成禁止エラーを同じ条件・同じ期待結果として扱うこと。
- 等価解がある角度変換で、物理的に同値な表現を理由なく1表現だけに固定すること。
- テストID、要求ID、UC IDの欠番を埋めるために既存番号を変更すること。
- テスト失敗を隠すためにアサーションを弱めること、または常に成功する固定値・Mockを置くこと。
- docstringやリンクの修正を理由に、製品コードやテストロジックを変更すること。
- テストIDを未リンクの裸文字で対応表に残すこと、または実在しないAPIアンカーを作ること。
- 要求仕様の本文をテストdocstringへ重複して管理すること。
