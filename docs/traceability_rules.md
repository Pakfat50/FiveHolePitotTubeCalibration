# トレーサビリティ運用ルール

## 1. 目的と適用範囲

本ルールは、5孔ピトー管較正Gコード生成GUIに機能を追加・変更する際に、要求、アーキテクチャ、製品コード、テスト仕様、テストコードを相互に追跡可能な状態へ維持するためのルールである。工程の順序と完了条件は[開発プロセスルール](development_process_guideline.md)に従い、本書はID・対応関係・リンク・アンカーの正本とする。製品コードの技術内容は製品コード開発ルール、テストコードの技術内容はテストコード開発ルールを正本とする。

対象となる成果物は次のとおりとする。

| 成果物 | ファイル | 役割 |
|---|---|---|
| 要求仕様書 | `docs/pitot_calibration_gui_spec.md` | EARS形式の要求と要求IDを定義する |
| アーキテクチャ設計書 | `docs/architecture_design.md` | ユースケース、設計要素、要求との対応を定義する |
| テスト仕様書 | `docs/test_specification.md` | 単体テスト/ユースケーステストと各IDの対応を定義する |
| 製品コードAPI | `docs/api.md` | 製品コードのDocstringからAPIを自動生成する |
| テストコードAPI | `docs/test-api.md` | テストコードのDocstringからテストAPIを自動生成する |
| テストコード開発ルール | `docs/test_doxygen_guideline.md` | テストレベル、検証方法、テストコード、ID・docstringの技術規約を定義する |

## 2. 基本原則

1. 要求ID、ユースケースID、テストIDは一度付与したら変更・再採番・再利用しない。
2. 削除された仕様やテストも、既存のトレーサビリティを壊さないため、必要に応じて「削除」と明記してIDを保持する。
3. 要求に対する関連成果物は、要求仕様書内で1つの関連成果物ブロックにまとめる。重複した関連成果物ブロックを作らない。
4. リンク先は、リンク元の種類に対応した成果物の該当セクションまたはAPIアンカーとする。別章の似た見出しや、リンク元自身の行への自己参照で代用しない。
5. Markdownのリンクは、原則としてサイト相対リンクまたはビルド時に生成するセマンティックマーカーを使う。GitHub Pagesの完全URLを本文へ埋め込まない。
6. マトリックスのID表示は、IDが1つだけの場合も含め、短縮表示とリンクを必須とする。例：`[096](#test-unit-096)`。
7. ドキュメントのリンク修正では、製品コードとテストコードの動作・ロジック・アサーションを変更しない。
8. 仕様変更を実装する場合は、実装変更とドキュメント/トレーサビリティ更新を別々に確認し、最終的に実装とドキュメントが一致していることを検証する。

## 3. ID体系

| ID | 用途 | 例 |
|---|---|---|
| `REQ-<カテゴリ>-NNN` | 要求仕様 | `REQ-SIM-007` |
| `UC-NN` | アーキテクチャ上のユースケース | `UC-05` |
| `TEST-UNIT-NNN` | 単体テスト仕様 | `TEST-UNIT-126` |
| `TEST-UC-NN-MM` | ユースケーステスト仕様 | `TEST-UC-05-09` |
| APIアンカー | 製品コードのモジュール/クラス/メソッド | `simulation.SimulationController.start` |
| テストAPIアンカー | テストコードのモジュール/クラス/テストメソッド | `tests.test_simulation.TestSimulation.test_start_sets_playing_state_at_first_point` |

要求カテゴリは既存の分類を維持する。現在の主なカテゴリは `INPUT`、`VALID`、`TRANS`、`POS`、`LIMIT`、`SCAN`、`GCODE`、`SIM`、`GUI` である。

## 4. 追跡関係とリンク先

| 起点 | 終点 | 表示・リンクのルール |
|---|---|---|
| 要求仕様 | アーキテクチャのユースケース | 対応する `UC-NN` を `ARCH` マーカーでリンクする。既存UCはアーキテクチャ設計書3.1～3.6の各セクションへ遷移させる |
| 要求仕様 | 製品コード | 実在するAPIアンカーを `API` マーカーでリンクする |
| 要求仕様 | 単体テスト仕様 | `TESTSPEC` マーカーで `test_specification` の該当テストへリンクする |
| アーキテクチャ設計 | 要求仕様 | 要求IDは `REQ` マーカーで要求仕様書の `#req-...` へリンクする。アーキテクチャ設計書内の行アンカーへの自己リンクにしない |
| アーキテクチャ設計 | ユースケーステスト | `UCTEST` マーカーで該当UCのテスト仕様へリンクする |
| テスト仕様 | 要求仕様 | 要求IDは `REQ` マーカーで要求仕様書の該当要求へリンクする |
| テスト仕様 | 製品コードAPI | モジュール/メソッド名を `API` マーカーでAPIページの実在アンカーへリンクする |
| テスト仕様 | テストコードAPI | `TESTCODE_SHORT` または既存の `TESTCODE` マーカーでテストAPIへリンクする |
| テスト仕様のIDマトリックス | 同一テスト仕様書の詳細行 | 短縮番号でも必ず `#test-unit-NNN` または `#test-uc-NN-MM` へリンクする |
| ユースケーステスト | アーキテクチャのユースケース | `ARCH` マーカーでアーキテクチャ設計書の該当UCへリンクする |

トレーサビリティの基本経路は次のとおりである。

`要求仕様 ⇄ ユースケース/アーキテクチャ ⇄ 製品コードAPI ⇄ テスト仕様 ⇄ テストコードAPI`

単体テストは要求IDへ、ユースケーステストは原則としてUC IDへトレースする。ユースケーステストを要求IDへ直接置き換えてはならない。

## 5. 要求仕様書の記述ルール

### 5.1 要求の追加

1. 新しい要求に未使用の `REQ-<カテゴリ>-NNN` を付与する。
2. 要求見出しに安定した `req-...` アンカーを付与する。自動スラグが期待どおりにならない見出しは、属性リストで明示的にアンカーを指定する。
3. 要求本文、受入条件、関連成果物を同じ要求IDに対応付ける。
4. 既存要求を分割・統合する場合も、既存IDを勝手に付け替えず、変更履歴または削除状態を明記する。

### 5.2 関連成果物

関連成果物は要求ごとに1回だけ記載し、成果物名とID/API名を正確に書く。例えば `REQ-SIM-007` は次のように記載する。

| 関連成果物 | 記載内容 |
|---|---|
| アーキテクチャ設計 | 対応するUC IDとユースケース名（例：UC-05「シミュレーションする」） |
| 製品コード | 実装クラス/メソッド名（例：`SimulationController.start`、`SimulationView.start_animation`） |
| テスト仕様 | 対応するテストID（例：`TEST-UNIT-126`） |

表示上のリンクが必要な場合は、成果物名やAPI名をセマンティックマーカーで記述し、リンク先URLを手書きしない。

## 6. アーキテクチャ設計書の記述ルール

### 6.1 ユースケース

- 既存のUC IDは変更しない。
- `UC-01`～`UC-06`は、アーキテクチャ設計書3.1～3.6の対応セクションへリンクできる安定アンカーを持たせる。
- 要求からユースケースへリンクするときは、章10や別の関連成果物欄ではなく、対応する3.1～3.6のUCセクションへリンクする。
- 新しいユースケースを追加する場合は、新しいUC IDと対応する3.xセクション、および安定アンカーを追加する。

### 6.2 要求仕様ID－クラス/メソッド トレーサビリティマトリックス

- INPUT列などの要求IDは、要求仕様書の該当要求へリンクする。
- 行の識別用アンカーを残す必要がある場合でも、表示される要求IDのリンク先は要求仕様書とする。
- 1つの要求に複数のクラス/メソッドが対応する場合は、すべての実在するAPI名を記載する。
- 製品コードAPIに存在しない推測名や、古いメソッド名を記載しない。

## 7. テスト仕様書の記述ルール

### 7.1 単体テスト仕様

各単体テストには、次を対応付ける。

- `TEST-UNIT-NNN`
- 1件以上の正確な要求ID
- テスト内容、入力/条件、期待結果、対象テストコード

要求IDは、要求仕様書への遷移が必要な表では `REQ` マーカーを使う。テストコードへの遷移が必要な表では `TESTCODE_SHORT` を使う。

### 7.2 要求仕様ID ↔ 単体テストIDマトリックス

- 要求IDは要求仕様書の該当要求へリンクする。
- テストIDは同一テスト仕様書の詳細行へリンクする。
- 要求IDの表示はカテゴリと番号が分かる短縮形を基本とし、リンク先は `#req-...` とする。
- 同一行に複数テストがある場合は、すべての番号を記載する。

### 7.3 モジュール/メソッド ↔ 単体テストID対応表

- モジュール/メソッド名は、製品コードAPIページの実在するクラス/メソッドアンカーへリンクする。
- 複数メソッドを1行にまとめる場合も、各メソッドを個別にリンクする。
- 単体テストIDは、1件だけの場合も短縮表示してリンクする。裸の `TEST-UNIT-NNN` や、リンク先のない手動アンカーだけの表示は禁止する。
- モジュール/メソッド名は、製品コードの実装名に合わせる。API上の正式名が変わった場合は、コード変更後にこの表も更新する。

### 7.4 ユースケーステスト

- ユースケーステストIDは `TEST-UC-NN-MM` とする。
- UC IDは `ARCH` マーカーでアーキテクチャ設計書の対応UCへリンクする。
- ユースケーステストの詳細行には、シナリオ、操作/条件、期待結果、対象テストコードを記載する。
- UC単位のマトリックスでは、テスト番号を短縮表示しても、すべての番号をリンク付きで記載する。

## 8. 製品コードAPIとテストコードAPIのルール

### 8.1 APIアンカー

製品コードAPIのリンク先は、mkdocstringsが生成した実際のIDを使用する。

- モジュール：`module`
- クラス：`module.Class`
- メソッド：`module.Class.method`

テストコードAPIは次の形式を基本とする。

`tests.<test_module>.<TestClass>.<test_method>`

APIアンカーは推測で作らず、公開されたAPIページのHTMLで `id` の存在を確認する。モジュール名やメソッド名の表示だけを変更して、別のAPIアンカーへリンクしてはならない。

### 8.2 APIマーカー

Markdown中では次のセマンティックマーカーを使用する。

| マーカー | 用途 |
|---|---|
| `API` | 製品コードAPIへの一般的なリンク |
| `API:...|表示名` | APIアンカーは維持しつつ表示名だけ変えるリンク |
| `TESTCODE_SHORT` | テストAPIへの短い表示「テストコード」 |
| `TESTCODE` | 登録済みのテストAPIリンクを特定の表示名で出す既存形式 |
| `CODE` | 既存の固定表示/固定リンクが必要な箇所で使う管理対象の別名 |

新しい製品コードAPIリンクは、原則として一般的な `API` マーカーを使う。`CODE` の固定マッピングを新設する場合は、リンク先APIアンカーの存在を確認してから `docs/hooks.py` の管理表へ追加する。

### 8.3 ソースコードDocstring中のID

製品コードAPI/テストコードAPIに表示されるDocstringでは、要求ID、TEST ID、UC IDを正確な文字列で記載する。生成HTMLでは `traceability-links-v2.js` が次のIDを自動リンクする。

- `REQ-...` → 要求仕様書
- `TEST-UNIT-...` / `TEST-UC-...` → テスト仕様書
- `UC-..` → アーキテクチャ設計書

自動リンク対象のIDを、リンクさせたい箇所でインラインコード、`pre`、または既存の`a`要素に閉じ込めない。自動リンク対象外の表示が必要なMarkdownでは、対応するセマンティックマーカーを使う。

## 9. セマンティックマーカーとアンカーの実装ルール

リンク生成は次の2段階で行う。

1. `docs/hooks.py` がMarkdown中のセマンティックマーカーをサイト相対リンクへ変換する。
2. `docs/javascripts/traceability-links-v2.js` が生成されたページ上の正確なID文字列を補助的にリンク化する。

主要なマーカーの記法例は次のとおりである。

- 要求仕様書：`[[REQ:REQ-SIM-007]]`
- アーキテクチャUC：`[[ARCH:UC-05]]`
- 製品コードAPI：`[[API:simulation.SimulationController.start]]`
- 表示名付きAPI：`[[API:gui.MainWindow|MainWindow]]`
- テスト仕様：`[[TESTSPEC:TEST-UNIT-126]]`
- UCテスト：`[[UCTEST:UC-05]]`
- テストコード短縮表示：`[[TESTCODE_SHORT:tests.test_simulation.TestSimulation.test_pause_stops_animation_and_keeps_current_point]]`
- アーキテクチャ行への戻りリンク：`[[ARCHREQ:REQ-SIM-007]]`

セマンティックマーカーのリンク先はサイト相対で生成する。`https://pakfat50.github.io/...` をソースMarkdownへ直接記述しない。

### 9.1 手動アンカー

自動生成見出しに依存するとIDが変わる箇所には、明示的な小文字アンカーを付ける。

| 対象 | アンカー形式 |
|---|---|
| 要求仕様 | `req-<category>-<number>` |
| アーキテクチャUC | `uc-<number>` |
| 単体テスト仕様 | `test-unit-<number>` |
| ユースケーステスト仕様 | `test-uc-<uc>-<number>` |

アンカーを作ることと、そこへのリンクを作ることは別である。要求仕様書へ遷移させるリンクを、マトリックス自身の行アンカーにしてはならない。

## 10. 一般文書リンクとHTMLリンクの扱い

サイト内のHTMLリンクは、トレーサビリティリンクと一般文書リンクに分けて管理する。

| HTMLリンクの種類 | 扱い |
|---|---|
| 要求/UC/API/TEST/テストコード間のリンク | 本ルールのトレーサビリティ対象。リンク先アンカーを必ず検証する |
| 同一ページの目次・見出しリンク | MkDocs/Materialの自動生成。見出し変更後にリンク切れを確認する |
| サイトナビゲーション、検索、トップページ | `mkdocs.yml` とテーマが生成。トレーサビリティIDのリンク先には使用しない |
| GitHubリポジトリ、編集、ソース表示リンク | MkDocsテーマが生成する保守用リンク。トレーサビリティには使用しない |
| `test_doxygen_guideline.md` などの通常文書リンク | 相対パスで記述し、対象ファイルの存在を確認する |
| MkDocs Materialなどの外部リンク | 外部依存先として管理し、要求/テストの追跡経路には含めない |

現行サイト監査で確認された、トレーサビリティ以外のリンクは上表の一般文書/サイト基盤リンクに分類される。新しい種類の外部リンクや自動生成リンクを追加する場合は、本ルールの分類を先に更新する。

## 11. トレーサビリティ更新手順

工程の順序と工程ごとの完了条件は[開発プロセスルール](development_process_guideline.md)に従う。本節では、各工程で発生した変更を対応関係とリンクへ反映する手順だけを定める。

1. 新しい要求・UC・TEST IDを既存IDの変更・再利用なしで整理する。
2. 要求仕様書の要求本文、受入条件、対応ユースケース、関連成果物を1つのブロックへ整える。
3. アーキテクチャ設計書の対応UC、クラス/メソッド、ユースケース経路を更新し、UCリンクを3.1〜3.6へ向ける。
4. 実装後に確定した製品コードAPI名とテストコードAPI名を、各対応表へ反映する。
5. テスト仕様書のTEST ID、要求/UC、テスト対象、期待結果、テストコード対応を更新する。
6. 要求 ↔ アーキテクチャ、要求 ↔ テスト、モジュール/メソッド ↔ 単体テスト、UC ↔ ユースケーステストの各マトリックスを更新する。
7. セマンティックマーカー、手動アンカー、短縮ID表示を本ルールに従って設定する。
8. API/テストAPIの生成、`mkdocs build --strict`相当のCI、公開HTMLのリンク監査を実施する。

製品コードの層・計算・API/docstringは製品コード開発ルール、テストコードの検証方法・docstringはテストコード開発ルールで確認する。
## 12. デプロイ後のリンク監査項目

- すべての要求IDリンクが要求仕様書の `#req-...` に到達する。
- 要求からのUCリンクが対応するアーキテクチャ設計書3.1～3.6へ到達する。
- すべてのAPIリンクに対応するAPIページの `id` が存在する。
- すべての単体テストIDリンクに対応する `#test-unit-...` が存在する。
- すべてのユースケーステストIDリンクに対応する `#test-uc-...` が存在する。
- テストコードリンクに対応するテストAPIアンカーが存在する。
- マトリックスの単一IDがフル表示や未リンクに戻っていない。
- リンク元と異なる種類のページへ誤遷移していない。
- 内部リンクに未定義の新しいリンクパターンがない。

リンク監査では、リンクの見た目だけでなく、公開HTMLの `href` とリンク先HTMLのアンカーIDを照合する。
